# History and time

This document records the storage and timeline decisions that are easy to
miss when changing the history code. Exact field layouts and constants are
authoritative in `src/data/historical_storage.h`,
`src/data/historical_storage.cpp`, and `src/time/time_service.cpp`.

## Datasets and routing

There are two logical datasets in one storage engine:

| Dataset | Sources | Purpose |
| --- | --- | --- |
| Real | ESP32 ADC, ADS1115, and UART | Device observations |
| Demo | Realtime Demo plus protected fixture files | Development and demonstration |

The active sensor source selects the recording dataset. The Settings → Data
catalog may inspect either dataset, but that filter does not install, copy,
reclassify, or redirect files. Usage and browser history always follow the
active source.

## Files and rows

History is stored under `/history/v1/real/` and `/history/v1/demo/`. A segment
name contains its dataset, nonzero boot session, first monotonic minute, and
closed-record count, for example:

```text
h1-r-s0000000123-m0000000000.open
h1-r-s0000000123-m0000000000-n0240.bin
```

Each minute row is a packed 56-byte `MinuteEnergyRecordV1` containing channel
and component energy, channel/component valid coverage, the configured-channel
mask, quality flags, and reserved fields. Coverage is what distinguishes a
measured zero from missing data. No history consumer should substitute zero
for an unavailable channel.

Segments close at 240 complete minute rows. Five rows are buffered and written
together as a 280-byte append, so the current sudden-power-loss policy can
lose zero to five minutes that were still in RAM.

## Recovery and retention

An interrupted `.open` file remains readable. Complete 56-byte rows are kept;
a torn trailing row is ignored. Older committed files are not rewritten during
recovery. Malformed names and dataset/name mismatches are ignored by the
catalog.

Each dataset has an independent 200-file cap. Real files cannot be evicted by
Demo activity. Demo fixture files count toward the Demo cap but are never
retention victims; the active file is never deleted.

Reset is dataset-scoped:

- Reset Real clears Real history only.
- Reset Demo clears recorded Demo history and restores protected fixtures.
- Development reset may clear both datasets and recreate only the fixtures.

## Time model

Every boot receives a persistent nonzero session ID. Record order and current
session queries work on monotonic minutes before wall time is known. NTP or the
browser can add a wall-clock anchor containing the session, monotonic instant,
UTC time, fixed UTC offset, source, and uncertainty.

Anchors are metadata; they do not rewrite measurement rows. Calendar queries
require wall time and use the persisted fixed offset. Rolling queries can use
the current session's exact monotonic timeline. Older unresolved sessions may
be placed in a rolling query with an explicit assumed restart gap, but that
placement is temporary and is never persisted or used by calendar/cycle views.

Material sensor coverage gaps and time uncertainty are separate. A fully
measured minute can have uncertain wall time, and an anchored minute can have
partial channel coverage.

## Demo fixtures

Demo session zero is reserved for protected fixture files. The fixture profile
is generated by `tools/build_demo_profile.py`; it preserves its source gap and
uses the normal V1 parser/query path. Firmware only replaces fixture files when
the fixture version changes. Fixture placement is anchored once, avoids overlap
with recorded Demo sessions, and never changes Real history.

## Queries and browser contract

The firmware catalogs by strict filenames, sizes, anchor metadata, and current
RAM state; it does not scan every row for normal catalog work. Queries seek
directly to overlapping fixed-size rows and return both timeline flags and
per-channel/component coverage.

The browser history API is asynchronous. It follows the active source and has
no Real/Demo query parameter. The Data catalog endpoint may request
`dataset=real|demo` for diagnostics. The binary response is VPH3: its exact
header and 80-byte bucket layout are defined by
`src/network/history_response_encoder.cpp` and parsed by
`web/src/lib/api.js`; update both sides together.
